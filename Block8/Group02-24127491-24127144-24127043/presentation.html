❯ MẬT KHẨU: SALT & SLOW HASH (BCRYPT COST 10)

Mật khẩu là bí mật dài hạn của người dùng. Tuyệt đối không bao giờ lưu plain text hoặc sử dụng các hàm băm nhanh (MD5, SHA-1, SHA-256) để lưu mật khẩu.

❌ TẠI SAO FAST HASH (SHA-256 / MD5) THẤT BẠI?
  • Thiết kế cho toàn vẹn dữ liệu: SHA-256 được thiết kế để chạy nhanh nhất có thể (hàng tỷ phép tính/giây trên chip ASIC/GPU).
  • Bị bẻ khóa dễ dàng: Một card đồ họa phổ thông (NVIDIA RTX 4090) có thể thử hơn 20 tỷ hash SHA-256/giây. Hacker có thể duyệt sạch mọi từ điển mật khẩu 8–10 ký tự chỉ trong vài phút.
  • Rainbow Table: Nếu không có Salt ngẫu nhiên, các bảng băm tính sẵn (Rainbow Table) có thể tra ngược mật khẩu tức thì.
✅ TẠI SAO BCRYPT LÀ CHUẨN MỰC BẢO MẬT?
  • Tự động sinh Salt ngẫu nhiên: Mỗi mật khẩu khi băm đều gắn 1 Salt 128-bit độc nhất. Hai người dùng có cùng mật khẩu Password@123 vẫn ra 2 chuỗi hash hoàn toàn khác nhau.
  • Slow Hash & Work Factor: Bcrypt sử dụng thuật toán băm chậm thích ứng (Eksblowfish). Dự án cấu hình Cost = 10 ($2^{10} = 1.024$ vòng lặp), mất ~100ms cho 1 lần tính toán trên CPU.
  • Triệt tiêu tấn công phần cứng: 100ms không ảnh hưởng trải nghiệm người dùng lúc đăng nhập, nhưng làm chậm tốc độ brute-force của hacker từ 20 tỷ hash/giây xuống còn dưới 1.000 hash/giây!

❯ OTP & RESET TOKEN: SHA-256 + TIMING-SAFE EQUAL

Khác với mật khẩu dài hạn, OTP và Reset Token là bí mật ngắn hạn (Ephemeral Secrets). Dự án áp dụng mô hình băm SHA-256 một chiều và so sánh an toàn thời gian.

❓ TOKEN NGẮN HẠN CÓ CẦN BCRYPT KHÔNG?

Trả lời: KHÔNG CẦN BCRYPT vì 2 nguyên nhân cốt lõi:

  • High Entropy / Short Expiry: Reset Token là chuỗi 32 bytes ngẫu nhiên mật mã học (256-bit entropy). Không gian mẫu $2^{256}$ là bất khả thi để brute-force.
  • OTP có giới hạn thử nghiệm (Rate Limit): Mã OTP 6 số chỉ cho phép thử tối đa 5 lần và hết hạn trong 10 phút. Kẻ tấn công không thể thử vét cạn offline.
  • Dùng SHA-256 lưu vào cột otpHash và tokenHash: DB bị lộ hacker vẫn không thể biết plain token gửi qua email.
⏱️ NGUY CƠ TIMING ATTACK & GIẢI PHÁP

Hiểm họa: Toán tử === so sánh chuỗi theo kiểu ngắt sớm (Early-return). Ký tự đầu tiên sai sẽ dừng ngay, ký tự đầu đúng sẽ mất nhiều thời gian hơn một chút.

  • Hacker đo độ trễ mạng micro-giây để đoán từng ký tự của token.
  • Giải pháp bắt buộc: Băm input sang SHA-256 buffer cùng độ dài 32-byte, sau đó dùng hàm chuẩn crypto.timingSafeEqual() để so sánh với thời gian cố định hằng số $O(1)$.
CODE THỰC TẾ: HÀM SO SÁNH AN TOÀN TRÁNH TIMING ATTACK src/utils/cryptoTokens.js 
function timingSafeCompare(userInput, storedHash) {
  if (!userInput || !storedHash) return false;
  
  // Băm input của người dùng bằng SHA-256 tạo thành Buffer độ dài 32 bytes
  const inputHashBuffer = crypto.createHash('sha256').update(String(userInput).trim()).digest();
  const storedHashBuffer = Buffer.from(storedHash, 'hex');

  if (inputHashBuffer.length !== storedHashBuffer.length) return false;

  // So sánh hằng số thời gian O(1) - không bị ngắt sớm, triệt tiêu Side-Channel Timing Attack
  return crypto.timingSafeEqual(inputHashBuffer, storedHashBuffer);
}

❯ SESSION ID VS SESSION DATA & 3 CỜ COOKIE

Trong kiến trúc SSR, phiên đăng nhập là Stateful. Trình duyệt chỉ giữ "vé định danh" (Session ID), còn toàn bộ thông tin nhạy cảm nằm an toàn trên PostgreSQL.

📦 1. SESSION ID TRÊN CLIENT VS SESSION DATA TRÊN SERVER
  • Client (Browser): Chỉ lưu chuỗi Session ID ký mật mã trong cookie tên sid. Client không giữ bất kỳ thông tin nào về role hay user ID.
  • Server (PostgreSQL): Bảng Session lưu bản ghi JSON phiên: { user: { id, name, role, status }, csrfToken }.
  • Lợi ích: Nếu tài khoản bị khóa hoặc đổi mật khẩu, server có thể xóa ngay bản ghi trong DB để vô hiệu hóa phiên lập tức.
🍪 2. BỘ BA CỜ COOKIE BẮT BUỘC
  • HttpOnly: Chặn hoàn toàn JavaScript truy cập cookie qua document.cookie. Ngăn chặn hacker đánh cắp phiên khi có lỗ hổng XSS.
  • SameSite=Lax: Không gửi cookie theo các request chéo trang độc hại (Cross-site POST). Giảm thiểu nguy cơ CSRF.
  • Secure: Chỉ gửi cookie qua kết nối mã hóa HTTPS (ở môi trường Production), chống đánh cắp gói tin qua Man-In-The-Middle.

❯ CHỐNG SESSION FIXATION & CSRF TOKEN PATTERN

Hai lỗ hổng kinh điển trên các ứng dụng SSR là Cố định phiên (Session Fixation) và Giả mạo yêu cầu chéo trang (Cross-Site Request Forgery).

🔄 1. TẤN CÔNG SESSION FIXATION LÀ GÌ?

Kịch bản: Kẻ tấn công tạo sẵn 1 Session ID ẩn danh trên server, dụ nạn nhân nhấp link để gán cookie đó. Khi nạn nhân đăng nhập thành công, nếu server không đổi Session ID, kẻ tấn công dùng lại Session ID cũ để chiếm tài khoản.

Giải pháp bắt buộc (Slide 33): Gọi req.session.regenerate() ngay khi đăng nhập để hủy bỏ Session ID ẩn danh và cấp 1 Session ID mới toanh gắn với quyền hạn người dùng.

🛡️ 2. CSRF SYNCHRONIZER TOKEN PATTERN

Nguyên lý: Trình duyệt tự động gửi cookie khi submit form. Trang web độc hại có thể lừa người dùng gửi request POST đổi thông tin.

  • Server sinh mã bí mật csrfToken (24 bytes hex) lưu trong session.
  • Render token vào thẻ ẩn trong mọi form: <input type="hidden" name="_csrf" value="...">.
  • Khi nhận request POST, middleware kiểm tra req.body._csrf === req.session.csrfToken. Trang web bên thứ 3 không thể đọc token này.
CODE THỰC TẾ: BẢO VỆ CSRF ĐỒNG BỘ VỚI MỌI METHOD THAY ĐỔI DỮ LIỆU src/middlewares/csrfMiddleware.js 
function verifyCsrfToken(req, res, next) {
  // Các phương thức an toàn (GET, HEAD, OPTIONS) không yêu cầu token
  if (['GET', 'HEAD', 'OPTIONS'].includes(req.method)) return next();

  const tokenFromForm = req.body?._csrf || req.headers['x-csrf-token'];
  const tokenInSession = req.session?.csrfToken;

  if (!tokenFromForm || !tokenInSession || tokenFromForm !== tokenInSession) {
    return res.status(403).render('403', {
      title: '403 - Lỗi CSRF',
      message: 'Yêu cầu bị từ chối do mã xác thực CSRF không hợp lệ hoặc phiên làm việc đã hết hạn.'
    });
  }
  return next();
}

❯ LÝ GIẢI LỰA CHỌN CÔNG NGHỆ (TECH STACK)

Mọi công nghệ trong dự án được lựa chọn dựa trên yêu cầu bảo mật nghiêm ngặt của bài tập, độ tin cậy và sự phù hợp hoàn hảo với kiến trúc SSR.

1. NODE.JS + EXPRESS 5 + EJS
  • Kiểm soát giao thức HTTP cấp thấp: Dễ dàng can thiệp header Set-Cookie, mã phản hồi 303 See Other, 429 Too Many Requests.
  • Render SSR an toàn: Render trực tiếp _csrf token và Cloudflare widget vào HTML thuần; không lưu session vào localStorage giúp loại bỏ hoàn toàn nguy cơ rò rỉ token qua XSS.
2. POSTGRESQL + PRISMA ORM
  • ACID Atomic Transactions: Hỗ trợ prisma.$transaction([...]) đảm bảo kích hoạt OTP (cập nhật User + đánh dấu usedAt) hoặc reset mật khẩu diễn ra nguyên tử tuyệt đối.
  • Strict Schemas: Ràng buộc chặt chẽ quan hệ 1:1, 1:N giữa 6 bảng xác thực và tự động tạo chỉ mục trên các cột tra cứu email chuẩn hóa.
3. CUSTOM PRISMA SESSION STORE
  • Phiên bền vững: Kế thừa session.Store lưu dữ liệu vào bảng Session trên PostgreSQL. Không mất phiên khi restart server như MemoryStore.
  • Quản lý phiên cấp độ DB: Có cột tường minh userId, cho phép thực thi lệnh hủy toàn bộ phiên của 1 người dùng (Multi-session revocation) chỉ bằng 1 câu lệnh deleteMany.
4. CLOUDFLARE TURNSTILE CAPTCHA
  • Trải nghiệm mượt mà (Zero Friction): Không bắt người dùng giải đố chọn đèn giao thông/biển báo phiền toái như Google reCAPTCHA v2.
  • Chống Bot & Brute-Force: Xác thực server-to-server qua /turnstile/v0/siteverify. Kết hợp bảng CaptchaChallenge một lần trong DB để ngăn chặn replay token.
5. BCRYPTJS + NODE CRYPTO
  • Phân chia nhiệm vụ đúng đắn: Dùng bcryptjs (Cost = 10) băm mật khẩu dài hạn; dùng Node crypto (SHA-256 + timingSafeEqual) băm OTP và Reset Token ngắn hạn.
  • Không phụ thuộc binary native build: bcryptjs chạy ổn định 100% trên mọi hệ điều hành (Windows, Linux, macOS) mà không gặp lỗi node-gyp.
6. NODEMAILER (SMTP)
  • Linh hoạt môi trường: Tích hợp chuẩn SMTP gửi email kích hoạt OTP và link reset mật khẩu.
  • Kiểm thử cục bộ: Hỗ trợ Mailpit / Ethereal Email khi dev trên máy cục bộ và Gmail SMTP khi triển khai thực tế.

❯ YÊU CẦU 3: GỬI LẠI MÃ OTP (POST /ACTIVATE/RESEND)

Chống spam email và ngăn chặn gian lận số lần thử nghiệm bằng 3 lớp khóa nghiêm ngặt: Cooldown 60s, giới hạn tối đa 5 lần gửi lại và bảo toàn số lần thử sai.

⏱️ 3 RÀNG BUỘC KỸ THUẬT QUAN TRỌNG NHẤT
  • 1. Cooldown 60 giây giữa 2 lần gửi: Server tính khoảng thời gian now - lastSentAt. Nếu dưới 60.000 ms → trả ngay HTTP 429.
  • 2. Giới hạn số lần gửi lại tối đa (Max 5 resends): Nếu resendCount >= 5 → khóa chức năng gửi lại, trả ngay HTTP 429.
  • 3. BẢO TOÀN ATTEMPTS (KHÔNG RESET VỀ 0): Khi sinh mã OTP mới, server ghi đè otpHash và gia hạn expiresAt, nhưng giữ nguyên giá trị attempts cũ. Kẻ tấn công không thể gửi lại OTP để xóa số lần nhập sai!

function requireAuth(req, res, next) {
  // 1. Chưa đăng nhập -> Chuyển hướng 303 về /login (Slide 54, 60)
  if (!req.session || !req.session.user) {
    return res.redirect(303, '/login');
  }

  // 2. Đã đăng nhập nhưng tài khoản đang ở trạng thái pending -> Hủy phiên và chặn (Slide 54)
  if (req.session.user.status === 'pending') {
    return req.session.destroy(() => {
      res.clearCookie('sid');
      return res.redirect(303, '/login?error=pending');
    });
  }

  return next();
}

❯ 6 CÂU HỎI VẤN ĐÁP BẢO VỆ ĐỒ ÁN (SLIDE 62)

Q1: TẠI SAO KHÔNG THỂ DÙNG SHA-256 ĐỂ BĂM MẬT KHẨU?

Trả lời: SHA-256 là hàm băm nhanh (hàng tỷ hash/giây trên GPU). Hacker có thể dùng card đồ họa chạy vét cạn (brute-force) từ điển chỉ trong vài phút. Mật khẩu bắt buộc phải dùng Bcrypt (hàm băm chậm có Salt và Cost Factor) để triệt tiêu năng lực tính toán phần cứng của kẻ tấn công.

Q2: TOKEN RESET MẬT KHẨU CÓ CẦN BĂM BCRYPT KHÔNG?

Trả lời: Không cần Bcrypt, chỉ cần SHA-256. Vì token reset là chuỗi ngẫu nhiên mật mã học 32 bytes (256-bit entropy cao), không gian mẫu $2^{256}$ là bất khả thi để đoán mò, đồng thời token có thời hạn ngắn (15 phút) và dùng 1 lần duy nhất.

Q3: TẠI SAO KHÔNG NÊN LƯU JWT TRONG LOCALSTORAGE?

Trả lời: localStorage có thể bị truy cập bởi bất kỳ đoạn mã JavaScript nào chạy trên trang. Nếu ứng dụng dính lỗ hổng XSS (qua thư viện bên thứ 3 hoặc input chưa escape), hacker có thể đánh cắp token ngay. SSR dùng Cookie HttpOnly giúp trình duyệt tự bảo vệ token khỏi JavaScript.

Q4: SESSION FIXATION DIỄN RA KHI NÀO VÀ KHẮC PHỤC RA SAO?

Trả lời: Xảy ra khi Session ID trước và sau khi đăng nhập giữ nguyên không đổi. Hacker gán Session ID của mình cho nạn nhân và đợi nạn nhân đăng nhập để chiếm quyền. Cách khắc phục: Luôn gọi req.session.regenerate() ngay khi đăng nhập để cấp Session ID mới toanh.

Q5: VÌ SAO CẦN REFERRER-POLICY: NO-REFERRER Ở TRANG RESET?

Trả lời: URL trang reset chứa token nhạy cảm (/reset?token=abc...). Nếu trang web tải hình ảnh, font hoặc link ngoài, trình duyệt sẽ tự động gửi kèm URL đầy đủ trong Header Referer, làm rò rỉ token reset cho bên thứ 3. Cờ no-referrer triệt tiêu nguy cơ này.

Q6: PHÂN BIỆT SAMESITE=LAX VÀ SAMESITE=STRICT?

Trả lời: Strict không bao giờ gửi cookie theo request từ trang khác (kể cả nhấp link thông thường). Lax cho phép gửi cookie với các điều hướng top-level an toàn (như bấm link GET), nhưng chặn tuyệt đối trong các request POST/PUT/DELETE từ trang ngoài, giúp cân bằng hoàn hảo giữa bảo mật CSRF và trải nghiệm người dùng.
